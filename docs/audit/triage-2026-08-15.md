## SCAL-05 — live Supabase Auth call on every authenticated request

### State at HEAD

The primary fix the finding asked for **exists and is committed** (`8763f37b`):

- `apps/api/src/lib/supabase-jwt.ts:87` — `verifySupabaseJwt(token, secret, nowMs)`. HS256 only
  (strict allow-list at `:103`, so `alg:none` and alg-confusion are refused), `timingSafeEqual`
  signature check `:111`, `aud` must include `authenticated` `:119` (without which the project's
  public anon key would authenticate as whatever `sub` it carries), `exp` enforced `:123`. No new
  dependency — `node:crypto` only.
- `apps/api/src/middlewares/auth.ts:285` — local verify first; **`null` falls through to the
  existing `supabaseAdmin.auth.getUser(token)` at `:295`**, so a rotated or mistyped secret degrades
  to today's behaviour rather than locking anyone out.
- The gate is `supabaseJwtConfig().enabled = !!process.env.SUPABASE_JWT_SECRET`
  (`supabase-jwt.ts:47-49`). **`SUPABASE_JWT_SECRET` does not appear in `render.yaml`.** Unset means
  every request still takes the remote path.

### Measured cost of the remote call (production, 2026-08-15)

Same endpoint (`/api/v1/payouts/balance`), 8 samples each, so the only difference is whether the
middleware reaches `getUser`:

| Request | result | min | median |
|---|---|---:|---:|
| No `Authorization` header (no Supabase call) | 401 | 0.245 s | ~0.265 s |
| Garbage `Bearer` (local verify refuses → falls through to GoTrue) | 401 | 0.346 s | ~0.388 s |

**Marginal cost of the remote `getUser`: ~101 ms (min-to-min), ~123 ms (median-to-median).** This
confirms the audit's "~100–300 ms" from production rather than from a model of it. Setting the
secret removes that ~101 ms from every authenticated request whose token is a valid project JWT, and
removes Supabase Auth's rate limit as the API's throughput ceiling.

### The cache, and its invalidation risk

`apps/api/src/lib/auth-cache.ts` already covers the finding's second half:

- Key = **SHA-256 of the whole token**, so an entry can only be read back by the exact token that
  produced it; a forged token hashes elsewhere and misses.
- Expiry = `min(60 s TTL, the token's own exp)`. `exp` is parsed **without** verifying the signature,
  which is sound in this direction only: it can shorten a lifetime, never grant trust.
- Bounded at 5,000 entries. `AUTH_CACHE_TTL_MS=0` disables it.
- The write happens **after** the blocked gate (`auth.ts:342`), so a suspended account is never cached.

**Two invalidation risks, both real, neither fatal:**

1. **`invalidateAuthUser` is called from exactly one place** — `apps/api/src/services/admin.service.ts:495`,
   inside `updateUser`. Six other writes mutate role assignments and never evict:
   `routes/admin-leads.ts:503`, `routes/auth.ts:962`, `routes/magic-link.ts:180`,
   `services/onboarding.service.ts:60`, `:255`, `:262`. A user who gains a role through
   self-onboarding or a magic link keeps the **pre-change role set for up to 60 s**. That is a
   permission-lag, not a permission-escalation (the roles were legitimately granted), but a
   provider who completes onboarding and immediately hits a role-gated route gets a 403 they
   cannot explain.
2. **The cache is per-process.** Render free runs one instance, so this is latent today; the moment
   the API scales past one container, an eviction on instance A does not evict instance B, and a ban
   bites on one container and not the other. Any move off single-instance must either drop the TTL
   to seconds or move eviction to a shared channel.

**Classification: `owner_gated`.** The code is shipped. The owner action is exactly one thing:
set `SUPABASE_JWT_SECRET` on the Render API service (`srv-d7mc2n8sfn5c73dfce0g`) to the value at
**Supabase dashboard → Settings → API → JWT secret**. It is safe to set and safe to unset — an
incorrect value degrades to the current remote path rather than failing closed. If the project uses
asymmetric (RS256/ES256) signing keys, leave it unset: `supabase-jwt.ts:103` refuses those by design
and they need a JWKS fetch that does not exist yet.

### Worst offenders — by growth class, not by count

**Measurement caveat, stated plainly:** the audit's per-query byte figures came from
`EXPLAIN (ANALYZE, SERIALIZE)` against 200k-row shadow tables. I could not reproduce that — there is

is labelled as such. It is still enough to separate the dangerous reads from the harmless ones,
which is what the finding actually needs.

**Only 5 of the 91 have no `where:` clause at all** — these are whole-table reads:

| Rank | Site | Model | Why it is the worst | Growth driver |
|---|---|---|---|---|
| 1 | `routes/admin-lead-conversion.ts:~99` | `outreachLog` | 6 columns, **entire table**, no bound of any kind | One row **per outbound message ever sent**. Fastest-growing table in the system and it never shrinks. |
| 2 | `routes/admin-lead-conversion.ts:~70` | `lead` | 4 columns, **entire table** | One row per prospect ever imported; the lead machinery exists to make this number large. |
| 3 | `routes/priests-public.ts:~144` | `priest` | `where` + `orderBy ratingAvg` but **no take**; selects `bio`, `languages[]`, `specializations[]` — the widest rows of the five | **The only one of the five on a PUBLIC, unauthenticated route.** It is the only unbounded scan an anonymous caller can trigger, and it grows with the supply side the business is trying to scale. |
| 4 | `services/admin.service.ts:~175` | `userRoleAssignment` | `where: { role }` + `distinct: ['userId']`, no take | For `role=DEVOTEE` this is one row per registered user. |
| 5 | `routes/admin-temples.ts:~78` | `temple` | 7 columns including the `timingInfo` JSON blob | Catalogue-sized (hundreds), so bounded in practice — lowest of the five. |
| 6 | `routes/admin-gurukuls.ts:~28` | `gurukul` | `where` is a variable that may be empty; `include: { owner }` | Catalogue-sized. |

Also worth naming, though it does carry a `where`:

- **`routes/store-admin.ts:~130`** — `storeProduct.findMany({ where: { storeProfileId }, orderBy })`
  with **no `select` and no `take`**: one merchant's entire catalogue, every column. Bounded by one
  merchant, unbounded in that merchant's success.

**Everything else in the 91 is defensible and should not be churned.** The bulk of the per-file
counts are `where: { id: { in: [...ids] } }` hydration reads keyed off an already-paginated page —
all 5 in `routes/admin.ts`, all 5 in `routes/admin-bookings.ts`, all 5 in `routes/store-orders.ts` —
bounded by construction. The rest are single-owner reads (`where: { userId }`,
`where: { bookingId }`, `where: { storeProfileId }`).

**Classification: `code_fixable_now`, narrow.** Six sites, not 91. The correct next change is
`take` + `orderBy` (plus a SQL `count()` for the true total, so bounding the page does not silently
turn the total into the page length — that is SCAL-09's defect) on ranks 1–4 and `store-admin:130`.
Rank 3 should be treated as the priority because it is publicly reachable.

**One note on the finding's prescribed fix:** it asks for "a lint rule or a test that fails on
`findMany(` without `take`/`cursor`". What exists is a ratchet, not a ban, and the ratchet file says
so honestly at its header. That is the right call — a blanket ban would fail on ~85 legitimately
bounded sites — but the finding's text should be updated to match, not the ratchet.

## DI-05 — pandit paid through the temple path sees ₹0

> **Diagnosis only. No file was edited — `booking.service.ts`, `bookings.ts`, `payment.service.ts`
> and `payout-requests.ts` are owned by another running task, and
> `bookings.reassign-mints-earning.di05.test.ts` is being edited in this working tree right now.**

### The primary defect is fixed. Two minting paths now exist, both committed:

1. **`apps/api/src/services/booking.service.ts:940-973`** — mints the `Commission` when
   `newStatus ∈ EARNING_ATTACH_STATUSES` (`:372-378` = `priest_assigned`, `in_progress`, `completed`,
   `video_uploaded`, `delivered`) and `row.priestId` is set. Guarded by `findFirst` on `bookingId`
   (idempotent, `:941-944`) and by `payment.count({ status: 'captured' }) > 0` (`:946-948`), so it
   cannot mint withdrawable balance for an unpaid booking. Writes `providerId = Priest.userId` and
   `amount = priestPayout` — correct per `commission-math.ts`.
2. **`apps/api/src/routes/bookings.ts` reassign block (~`:1300-1340`)** — mints when the
   `commission.updateMany` above it matched **0** rows, which is exactly the temple-path case, with
   the same three guards.

The original early return is still there and still correct —
`apps/api/src/services/payment.service.ts:250` `if (!booking || !booking.priestId) return;` — it is
no longer the whole story because two later paths now cover it.

### Residual 1 — two assignment paths bypass the mint entirely (**the precise root cause**)

Both set `priestId` **and** `status: 'priest_assigned'` with a **raw `pujaBooking.update`**, never
entering `updateBookingStatus`, so the mint at `booking.service.ts:940` never runs:

- **`apps/api/src/services/dispatch.service.ts:397-400`**
  `tx.pujaBooking.update({ where: { id: bookingId }, data: { priestId, status: 'priest_assigned', assignedVia: 'broadcast', offerExpiresAt: null } })`
- **`apps/api/src/services/priest.service.ts:373-385`**
  `prisma.pujaBooking.update({ where: { id: bookingId }, data: { priestId, status: 'priest_assigned' } })`

`'priest_assigned'` **is** in `EARNING_ATTACH_STATUSES`, so the intent was for the mint to fire on
exactly these transitions. It does not. **Consequence:** a pandit who wins a dispatch broadcast, or
who accepts a booking in his own portal, still opens `/payouts/balance` and sees **₹0** — the
finding's own screen — until the booking next moves through `updateBookingStatus` at `in_progress`.
The money is not lost, but the window is the whole period between accepting a puja and starting it,
which is precisely when a new supplier decides whether to trust the platform.

**Load-bearing caution for whoever fixes this:** both call sites write `priestId` alongside several
other columns in one update, and the mint reads `row.priestId` from inside the transaction, so
ordering matters. The mint must run **after** the update commits its `priestId`, inside the same
transaction, with the same three guards — not before.

### Residual 2 — the two payout rails are only ONE-WAY exclusive

- `apps/api/src/services/payment.service.ts:1455+` — `createPriestPayout` **does** refuse when a live
  `Commission` already owns the booking. That direction is guarded.
- `apps/api/src/services/booking.service.ts:941-944` — the new mint checks **only**
  `tx.commission.findFirst`. It never checks `priestPayout`.

`delivered` is in `EARNING_ATTACH_STATUSES` and `video_uploaded → delivered` is a legal transition
(`VALID_TRANSITIONS`, `booking.service.ts:352-360`). So a **legacy** temple-path booking that already
carries a pending `PriestPayout` row mints a `Commission` on its next transition and becomes payable
on **both rails at once** — visible at `/payouts/pandit/mine` (`routes/payouts.ts:38`) **and**
`/payouts/balance`. New bookings are safe only because the ordering happens to favour them. The
guard's own comment at `payment.service.ts:1444-1447` ("temple-path… bookings never get one") is now
stale. **This is a double-payable, which is worse than the bug DI-05 fixed**, and it needs either a
`priestPayout.findFirst` in the mint's guard or a one-time reconciliation of legacy rows.

### Residual 3 — "four surfaces, four numbers" is untouched

`apps/api/src/services/payout.service.ts` contains **one** textual reference to `PriestPayout` and it
is in a comment at `:5`. `getPayoutBalance` (`:181-221`) sums `Commission` only — three
`commission.aggregate({ _sum: { amount } })` calls via `sumCommissionAmounts` (`:173-178`). So
`/payouts/balance` and `/payouts/pandit/mine` still answer independently, and a pandit with legacy
`PriestPayout` rows still sees two different truths about what he is owed.

**Classification: `code_fixable_now`, three items, all located above.** Priority order: residual 2
(double-payable) before residual 1 (₹0 window) before residual 3 (reporting divergence).
