- **File:** `apps/api/src/routes/auth.ts`
- **Test:** E:\NewClaude\bhaktisetu\apps\api\src\routes\auth.test.ts — `POST /login` writes an `INSERT INTO refresh_token_jtis` whose 2nd arg is a 64-char sha256 hex (asserted NOT equal to the plaintext refresh token) and whose 3rd arg is the Supabase user id; and a ledger write that rejects still returns 200 with a usable access token.

Seeding is best-effort by design: a ledger write failure degrades replay detection back to Supabase's native rotation rather than blocking a valid login. The rotation guard is needed because inside GoTrue's reuse-interval a retry can return the SAME refresh token; burning it there would make the next legitimate refresh look like a replay and revoke every session the user has.
