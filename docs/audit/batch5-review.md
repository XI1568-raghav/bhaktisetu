### Concerns
#### [should-fix] processPayout can still 'complete' a REJECTED or FAILED PayoutRequest whose commissions were already unlinked, producing exactly the hollow completed request the RV-06 write-up claims to have eliminated. The idempotency guard at payout.service.ts:224 only short-circuits on status 'completed' — it does not refuse re-processing of 'rejected'/'failed', and the complete branch (226-240) never asserts that the request still owns any commissions or that their sum matches req.amount.

- **Where:** `apps/api/src/services/payout.service.ts:224`
- **Why it matters:** RV-06 closed the creation side of the hollow-request problem but the write-up asserts the whole vector is closed ('left a hollow PayoutRequest an admin could complete for a second full transfer'). The completion side is unchanged. The reject path at payout.service.ts:253-256 unlinks the commissions and returns them to the withdrawable balance, so a rejected request is precisely a hollow request sitting in the admin list — and completing it fires a 'Payout sent Rs X' notification (259-266) to the provider for money that is simultaneously still claimable through a newer request.
- **Suggested fix:** Inside the transaction, refuse action='complete' unless req.status is 'pending' or 'processing', and before flipping the request to completed assert the linked set is non-empty and consistent: `const linked = await tx.commission.findMany({ where: { payoutRequestId: payoutId }, select: { amount: true, status: true } });` then throw if `!linked.length`, if any row is not PENDING, or if the Prisma.Decimal sum of linked amounts !== req.amount. Also scope the PAID updateMany at 236-239 to `status: 'PENDING'` so a REVERSED row can never be resurrected to PAID.

#### [should-fix] The RV-05 change removes the only thing that used to suppress duplicate weekly settlements, and nothing replaced it. The docstring precondition 'and no in-flight request' was deleted (payout.service.ts:278-280) and runWeeklySettlement (301-321) now creates a fresh PayoutRequest for a provider every week even when last week's is still 'pending', with no cap and no dedupe.

- **Where:** `apps/api/src/services/payout.service.ts:320`
- **Why it matters:** The money itself is safe — each request owns a disjoint commission set and processPayout only touches `payoutRequestId: payoutId` — so this is not a double-pay by itself. But the admin queue now accumulates N indistinguishable pending rows per provider, and by the fixing agent's own note (docs/audit/batch5-agent-fixes.md:150) listPayoutRequests exposes no linked-commission count, so an admin literally cannot tell two pending requests for the same provider apart. That is the realistic path into concern #1: an admin who assumes the extras are duplicates rejects one, then later re-completes it. Under the old (buggy) netting these rows mostly fell below WEEKLY_SETTLE_MIN_INR and the sweep skipped them, so this exposure is new with this diff.
- **Suggested fix:** Gate the cron only (leave self-serve alone): before calling requestPayout, skip the provider when `await prisma.payoutRequest.count({ where: { providerId, status: { in: ['pending','processing'] } } }) > 0`, counting it into a new skippedInFlight bucket. Separately, add a linked-commission count / linked-sum to listPayoutRequests (payout.service.ts:347-365) so an admin can distinguish requests and spot a hollow one.

#### [nit] getPayoutBalance still float-sums money — `s + Number(r.amount)` at payout.service.ts:55, 61 and 72 — inside the very function RV-05 rewrote, while the RV-06 test the same agent added (payout.service.test.ts:201) asserts that float-summing Decimal amounts is wrong.

- **Where:** `apps/api/src/services/payout.service.ts:55`
- **Why it matters:** No money moves wrong today: the values only feed display and two coarse gates (>= MIN_PAYOUT_INR 1 at line 146, >= WEEKLY_SETTLE_MIN_INR 100 at line 304), all amounts are Decimal(10,2), and Math.round(x*100)/100 absorbs the drift. But it violates the project's immutable 'money is Prisma.Decimal — never JS float arithmetic' rule in a money function that was just edited, and it leaves the codebase self-contradictory about the same defect class.
- **Suggested fix:** Reduce with Prisma.Decimal exactly as requestPayout now does (`rows.reduce((s, r) => s.add(new Prisma.Decimal(r.amount)), new Prisma.Decimal(0))`) and convert to number only at the return boundary (lines 84-88), e.g. `availableInr: pending.toDecimalPlaces(2).toNumber()`.

#### [nit] The interactive transaction at payout.service.ts:150 uses Prisma's default 5s timeout / 2s maxWait, but the loser of a genuine race blocks on the winner's row locks inside it. Separately, the link now uses `id: { in: rows.map(r => r.id) }` (line 188) where the previous code used a predicate scan, so the statement carries one bind parameter per unlinked commission.

- **Where:** `apps/api/src/services/payout.service.ts:150`
- **Why it matters:** Both are money-safe — a P2028 timeout still rolls the transaction back, so the fix stays fail-closed. The consequences are cosmetic/operational: on a slow winner the loser gets a raw Prisma error message instead of PAYOUT_CONCURRENT_REQUEST_ERROR, and routes/payout-requests.ts:71 forwards that raw message verbatim to the provider as a 400. #### [nit] runWeeklySettlement hardcodes `'PANDIT' as ProviderRole` for every provider it settles (payout.service.ts:320), so an astrologer's or store owner's auto-created PayoutRequest is stamped with the wrong role.

- **Where:** `apps/api/src/services/payout.service.ts:320`
