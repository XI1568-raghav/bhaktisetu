### RV-05 — payout-engine

- **File:** `apps/api/src/services/payout.service.ts`
- **Test:** apps/api/src/services/payout.service.test.ts — 'RV-05: available is the unlinked PENDING sum and never nets off in-flight' (the audit's worked example: 9,000 new + 5,000 in flight -> available 9,000 / pending 5,000, previously 4,000), 'RV-05: stays positive when in-flight exceeds newly earned (no lockout)' (2,000 new vs 5,000 in flight -> 2,000, previously -3,000), 'reports PAID separately as paidOut'. The pre-existing test that ENCODED the bug (asserted availableInr === 250 for 350 pending / 100 in-flight, with the comment 'in-flight (part of the 350)') was rewritten — its premise was wrong.

**What changed.** getPayoutBalance now returns `availableInr: round2(pending)` instead of `round2(pending - inFlight)`. The in-flight query and `pendingInr` are unchanged — in-flight is still computed and reported separately, it is just no longer subtracted. Added a WHY comment at the return site tagged "RV-05 (2026-08-10)" explaining the disjointness, plus a one-line comment on the inFlight query stating it is display-only. Also corrected two stale comments that encoded the bug: the inline note in runWeeklySettlement (which claimed availableInr would be 0 when a request is in flight) and the runWeeklySettlement docstring's "and no in-flight request" precondition.

**Why it is correct.** The `pending` query filters `payoutRequestId: null`; the `inFlight` query filters on the to-one relation `payoutRequest: { status: { in: ['pending','processing'] } }`, and a Prisma to-one relation filter never matches a row whose FK is NULL. The two sets are therefore provably disjoint, so the subtraction removed money that was never in the sum. It was not display-only: the returned availableInr sized the PayoutRequest while requestPayout linked ALL unlinked commissions to it, so on completion every linked row flipped to PAID and the difference (min(inFlight, newEarnings)) was destroyed in the platform's favour — recurring every Monday via master-cron -> runWeeklySettlement. `pending` alone is the correct withdrawable figure, and it can no longer go negative (the audit's inverse case: in-flight 5,000 vs new 2,000 used to return -3,000, disabling Withdraw and throwing 'No withdrawable balance' on money already earned). No other caller semantics change: routes/payout-requests.ts GET /balance and apps/web /payouts still read availableInr = withdrawable now, pendingInr = in flight.

### RV-06 — payout-engine

- **File:** `apps/api/src/services/payout.service.ts`
- **Test:** apps/api/src/services/payout.service.test.ts — 'RV-06: sizes the request from the rows read INSIDE the transaction, not the pre-check' (pre-check sees 4,000, tx sees 9,000 -> request created for 9,000 and updateMany scoped to exactly those ids with the payoutRequestId:null guard); 'RV-06: sums money as Decimal — no float drift' (6499.03+1625.48+8385.18 -> '16509.69'; the test also asserts the float sum is NOT 16509.69); 'RV-06: rejects when fewer rows link than were selected (concurrent claim)'; 'RV-06: refuses when the ledger emptied between the pre-check and the transaction' (no PayoutRequest created); and the headline race test 'two concurrent withdrawals settle ONE request for the balance, not two' — an in-memory Commission/PayoutRequest ledger where updateMany re-evaluates its predicate at write time and a throwing transaction rolls back only its own writes, with the first updateMany gated so the second caller commits in between. Asserts the loser rejects with PAYOUT_CONCURRENT_REQUEST_ERROR, exactly one request survives, its amount is the full 20,000, and every commission is linked to it. That test fails against the old implementation (two 20,000 requests for a 20,000 balance).

**What changed.** requestPayout was restructured. The outside-the-transaction getPayoutBalance call is retained ONLY as a fail-fast pre-check (renamed to `preview`, commented as advisory and never used to size anything). Inside prisma.$transaction it now: (1) re-reads `tx.commission.findMany({ where: { providerId, status: 'PENDING', payoutRequestId: null }, select: { id: true, amount: true } })`; (2) throws 'No withdrawable balance.' if that set is empty or sums below MIN_PAYOUT_INR; (3) sums with Prisma.Decimal (added `import { Prisma } from '@prisma/client'`) and creates the PayoutRequest with `amount: total`, i.e. sized from exactly the rows it is about to link; (4) links with `updateMany({ where: { id: { in: ids }, status: 'PENDING', payoutRequestId: null }, ... })` and throws the new exported `PAYOUT_CONCURRENT_REQUEST_ERROR` if `linked.count !== rows.length`. The trailing `.then()` chain became a plain await so the notification body uses the created request's real amount (`Number(created.amount)`) rather than the stale outside read.

**Why it is correct.** The double-spend needed two things: an amount taken from a read outside the transaction, and no check that the commissions were still unclaimed. Both are gone. The link predicate `payoutRequestId: null` is the guard: under READ COMMITTED the losing transaction blocks on the winner's row locks, re-evaluates via EvalPlanQual, finds the FK no longer NULL, and matches fewer rows than it selected — previously that silently returned count 0 and left a hollow PayoutRequest an admin could complete for a second full transfer; now it throws inside the transaction so the request row is rolled back. Sizing from the linked rows also removes the RV-05 residue permanently: request amount is by construction equal to the sum of the commissions it owns, so a completed request can never mark more money PAID than it transferred. The throw surfaces via routes/payout-requests.ts:70-72 as a 400 with a retryable message, matching how every other requestPayout error already behaves, and runWeeklySettlement already swallows per-provider failures (errors++) so a losing sweep iteration cannot abort the batch. Money is summed as Prisma.Decimal, never float. I did NOT add the DB-level partial unique index the verifier also recommends — that is a schema change (see needsOwner).

### RV-15 — booking-service

- **File:** `apps/api/src/services/booking.service.ts`
- **Test:** src/services/booking.service.test.ts — 3 cases in createBooking: 'locks the slot and re-checks capacity inside the create transaction' (asserts the pg_advisory_xact_lock SQL, the exact key `puja-slot:offering-1:2026-12-25:10:00`, two counts, one create), 'rejects when the slot fills between the pre-check and the locked re-count' (count returns 4 then 5 -> throws, no row written), 'still books when the advisory lock statement is unavailable'. **What changed.** createBooking's capacity count is now a two-stage check. The existing count stays as a cheap pre-check (preserving the fast failure and the current error ordering), and the booking insert moved into a `prisma.$transaction` that first takes a transaction-scoped Postgres advisory lock keyed on offering+date+slot (`SELECT pg_advisory_xact_lock(hashtextextended($1, 0))`) and then re-runs the authoritative count on the tx client before creating. Extracted `lockSlot`, `assertSlotCapacity` and `slotKeyFor` as module helpers, reused by rescheduleBooking. The lock is best-effort: if the statement cannot run it is logged and the flow falls through to the re-count.

**Why it is correct.** Per the verifier's explicit correction, a plain $transaction would NOT fix this — under READ COMMITTED (Postgres' default; Prisma passes no isolationLevel) both racers still see the pre-insert count. The advisory lock serialises everyone contending for the same slot key: the second racer blocks until the first COMMITs, then re-counts and sees the new row. It needs no schema change, and `pg_advisory_xact_lock` releases at COMMIT so it is safe under Supabase's transaction-mode pooler (a session-level lock would leak across pooled clients). It also collapses the 15-100ms window created by the 2-4 intervening round-trips (user lookup, pinned-priest lookup, booking-number collision retries, address lookup), which now all run BEFORE the transaction opens, keeping the lock hold short. This mirrors the repo's existing correct solution at routes/yatra-packages.ts:140-171. Degrading rather than throwing when the lock statement fails is deliberate: falling back to the old racy behaviour is strictly better than failing 100% of bookings. The durable fix is a partial unique index (owner-gated, reported).

(3) Every path is clamped to what is still refundable (`paid - payment.refundAmount`), so no path can over-refund; a fully-refunded payment now throws instead of hitting Razorpay. (4) Payment query widened from `status: 'captured'` to `status: { in: ['captured','partially_refunded'] }` so an admin can top a partial up; `refunded` stays excluded, preserving the double-refund guard. (5) Payment status is now `refunded` vs `partially_refunded` computed from `refundAmount + alreadyRefunded >= paid`, and `refundAmount` accumulates rather than overwrites. (6) The booking only flips to `status: 'refunded'` on a full refund; on a partial it keeps its status and its `cancellationReason` is rewritten to `[partially-refunded <amt>] ...`. (7) The two writes now run inside `prisma.$transaction`. (8) A never-cancelled booking (no `cancelledAt` and status != 'cancelled') now throws on the ladder path instead of defaulting. (9) All arithmetic is Prisma.Decimal end-to-end with one `.mul(100).toFixed(0)` conversion for Razorpay paise. `RefundResult` gained optional `tierLabel` / `refundFraction`. The Commission write at ~payment.service.ts:228-236 (S2C-15/RV-04) was NOT touched, and neither were the Stripe imports — the diff removes only lines inside processRefund.

**Why it is correct.** The finding is that this method had no amount parameter and always sent `Math.round(Number(payment.amount)*100)` paise. It now sends the ladder amount: on the audit's own scenario (Rs 1,100, cancelled 12h before an 18:00 slot) the 4h tier at refundFraction 0.5 yields Rs 550 / 55,000 paise instead of Rs 1,100 / 110,000 — the Rs 550 cancellation fee that `cancellationFeeToPriestFraction: 1.0` earmarks as pandit compensation stays with the pandit. It mirrors refund.service.processRefund on every axis the verifier named: same policy source (snapshot with default fallback), same tier-at-cancellation-time rule, same partial-vs-full payment status, same booking-status rule, same $transaction. The `[refund-requested]` marker rewrite on a partial is load-bearing and not cosmetic: processAutoRefunds selects on `cancellationReason.startsWith(REFUND_REQUESTED_MARKER)` with `status: 'cancelled'`, and its own captured-payment finder accepts `partially_refunded` — leaving the marker would have let the cron refund the same booking a second time an hour later, so the partial path would have created a NEW double-refund bug. The never-cancelled guard exists because applying the ladder there is meaningless (hoursUntilSlot is negative, every tier fails its minHoursBefore, and cancellation.service's `?? tiers[last]` fallback would silently hand back 25% on a delivered puja) — the old code silently refunded 100% there, so refusing and forcing the admin to state intent is strictly safer than either default. Money never leaves Decimal except for the single integer-paise conversion Razorpay's API requires.
