## Money-path verdict

No. It is not safe to take real payments on this system right now, and it is specifically not safe to switch on the live Stripe key. Domestic Razorpay puja bookings are closer to safe than the rest — the capture, the 20/80 split into booking.platformCommission/priestPayout, and the PriestPayout rail that actually pays pandits are all correct — but everything AROUND the capture (refunds, cancellations, reschedules, temple share, the unified payout engine) is broken in ways that move or destroy real money, and there is no automated reconciliation anywhere to catch it. Top three financial risks, in rupee terms. FIRST, the NRI checkout bills rupees as dollars: apps/api/src/routes/bookings.ts:1091 multiplies an INR base price by 9 and hands the raw product to Stripe as USD cents with no FX divide, so a Rs 1,100 puja that should cost $118.56 charges $9,900.00 — an 83.5x overcharge, ~Rs 8,18,730 of unearned cash and pure chargeback liability per booking. It is on by DEFAULT for any visitor whose browser timezone is not Asia/Kolkata, not just flagged NRI users. Today it only 500s because STRIPE_SECRET_KEY is unset; the day that key is set — an explicitly pending founder item — it charges silently. Fix this before anything else, and verify the key is not already set. SECOND, refunds are simultaneously too generous and structurally incomplete: every auto-processed refund pays 100% instead of the 100/75/50/25/0 ladder (S2C-14, plus the admin Approve button and the admin payments endpoint, which has no amount parameter at all), and the refund transaction writes only two rows — it never unwinds the provider Commission or the TemplePayout. On a Rs 5,000 refunded booking the devotee gets Rs 5,000 back while Rs 1,000 stays withdrawable to the priest and Rs 250 stays pending to the temple: ~Rs 6,250 out on a booking that earned Rs 0, with no REVERSED state in the schema to claw it back. THIRD, the payout engine is arithmetically wrong in two independent ways: apps/api/src/services/payout.service.ts:73 subtracts in-flight commissions from a set that provably excludes them, so a provider with Rs 5,000 in flight and Rs 9,000 newly earned is paid Rs 4,000 while ALL Rs 9,000 of their commissions are marked PAID (Rs 5,000 destroyed, and it recurs automatically every Monday via the settlement cron); and requestPayout reads the balance outside its own transaction with no uniqueness constraint, so a double-click mints two PayoutRequests for one balance — Rs 40,000 transferred against Rs 20,000 of earnings. The only thing keeping both inert is that provider_kyc.verified is never set to true anywhere in the codebase, which is not a control, it is an accident. Two more that are not top-three by rupees but are commercial-integrity failures you should not ship past: temples receive Rs 0.00 on 100% of paid bookings because the sole TemplePayout writer sits on a code path no paid booking can reach (booking.service.ts:404), and video proof — an immutable business rule — is not enforced anywhere in the state machine, so a booking can walk to 'delivered' with videoProofUrl null and mint a Rs 2,799 priest payout. Minimum before taking money at any volume: kill or fix the USD path, apply the ladder in refund.service and add refund-time ledger reversal, replace `pending - inFlight` with `pending` and add a partial unique index on in-flight payout requests, move the temple-share write into writePujaCommissionOnConfirm, and add a videoProofUrl predicate to the video_uploaded transition.

## Subsystem summaries

- commission-direction — The Commission ledger is written with the PLATFORM's cut in the field the payout engine documents and reads as the PROVIDER's net share (payment.service.ts:232 and again at booking.service.ts:378), and keyed on Priest.id where every reader passes User.id. The key bug currently masks the amount bug, so nothing is mis-paid today; fixing the key alone flips pandits from Rs 880 to Rs 220 on a Rs 1,100 puja. Both halves plus the duplicate non-transactional writer must land in one commit, with a UNIQUE index on commissions.booking_id. Separately, Priest.commissionRate defaults to 0.70, so pinned-priest bookings run 70/30 in production, not 20/80.
- refund-ladder — The published 100/75/50/25/0 ladder is computed for display and never applied to money. There are TWO refund implementations: refund.service.processRefund CAN do partials but every caller passes refundType:'full' (S2C-14, including the admin Approve button which posts no body at all), and payment.service.processRefund has no amount parameter, so no caller could ever apply the ladder without a signature change. Every refund that fires today is 100%, over-refunding Rs 275 at the 24-48h tier and Rs 550 at the 4-24h tier on a Rs 1,100 booking — and cancellationFeeToPriestFraction:1.0 means the loser is the pandit, who has zero consumers creating that compensation row anyway.
- cancel-path — The primary Cancel button is broken end to end. The service writes three columns and initiates no refund, and the cron only picks up bookings carrying a '[refund-requested]' marker that cancelBooking never writes, so money sits until an admin manually spots it in the refunds list. The web button then ignores the response entirely and renders 'cancelled, refund will be processed' even on a 409/403. And when a refund does eventually run, it never unwinds the provider Commission or the TemplePayout — the ledger keeps paying out on a booking that earned nothing.
- refund-safety — The scary claims here are false and the quiet one is true. No double gateway refund is possible (captured-status filter + Razorpay's refundable-amount cap + a refund.created webhook backstop), and no float coercion anywhere in this subsystem can misstate a rupee — worst case is Rs 0.01 on a temple share at an exact half-paisa tie. What IS real: payment.service.processRefund's three writes are non-atomic, so a crash mid-flight can leave a refunded booking still eligible to mint a priest payout; and the payout-balance query these claims pointed at contains a genuine, non-float money bug.
- payout-engine — Arithmetically wrong in two independent ways and currently inert only by accident. getPayoutBalance subtracts in-flight commissions from a set that provably excludes them, so providers are short-paid by exactly the in-flight amount while ALL their commissions are marked PAID — and it reproduces automatically every Monday via the settlement cron. requestPayout reads that balance outside its own transaction with no uniqueness constraint, so a double-click mints two requests for one balance. Nothing moves today only because provider_kyc.verified is never set to true anywhere in the codebase, and because puja commissions are keyed on the wrong id — two bugs acting as an accidental safety interlock. The unified path also has no Aadhaar check at all, so rule 4 survives only via the legacy createPriestPayout rail.
- temple-share — Completely non-functional, and inverted. The sole TemplePayout writer lives inside updateBookingStatus, which none of the three real payment-confirm paths call — they all flip status inline. The only route that CAN reach it is a manual PATCH to 'confirmed' on a booking still in pending_payment, i.e. an UNPAID booking, while every genuinely paid booking is permanently locked out by VALID_TRANSITIONS. Temples receive Rs 0.00 on 100% of paid bookings, the temple-portal payouts page reads 0/0 forever, and the dead code additionally computes 5% of priceAmount (including platform and prasad-delivery fees) via a Number() coercion. Fully backfillable.
- nri-usd — The single worst defect in the audit. basePrice x 9 is computed in rupees and handed to Stripe as USD cents with no FX division anywhere on the path; the repo's own correct helper (lib/pricing.ts, which divides by 83.5) is dead code imported by nothing but its test, and the GBP path elsewhere divides correctly while the USD path does not. The web checkout hard-codes the same broken math and displays '$9,900'. It triggers by default on browser timezone, not on the isNri flag. Currently masked only by a missing Stripe key — there is no configuration in which this route bills correctly.
- races — Two claims, one real. Slot capacity is a genuine count-then-create TOCTOU with a 15-100ms window, no transaction, no lock and no unique constraint — bounded overshoot, ~Rs 50-100 net loss per oversold booking, but it becomes materially likely at festival peaks and the repo already solves the identical problem correctly with SELECT ... FOR UPDATE in yatra-packages.ts. The booking-number collision claim is refuted: the @unique index is the real backstop, the residual probability is ~1e-24, and the create precedes any payment intent so no money is ever at risk.
- reschedule-window — The worst-audited surface in the codebase: zero test coverage across the whole cluster. Reschedule validates NOTHING about the new date or slot — not the availableSlots whitelist, not maxBookingsPerSlot, not real futurity (a booking can be moved into the past, which then traps it because cancel, reschedule and request-refund all reject it as 'within 24 hours'). Separately, cancel and reschedule both measure the 24h window from midnight of the scheduled DAY rather than the slot time, denying devotees up to 23h of their entitled window, while a sibling endpoint one file away does the same computation correctly. The cancel-quote endpoint makes the same midnight error in the other direction, quoting Rs 275 where Rs 550 is owed and returning a negative hoursUntilSlot.
- business-rules — Two of the seven immutable rules are unenforced in code. Rule 1 (mandatory video proof): PATCH /bookings/:id walks completed -> video_uploaded -> delivered with videoProofUrl null and mints the priest payout on the way, while all three would-be compensating controls filter on statuses that structurally exclude the resulting row — and the admin's only remediation endpoint returns 409 precisely because there is no proof to flag. Rule 6 (temples verified before live): the temple-anchored booking path never selects isVerified or status at all, and list/detail/offering reads all serve pending_review temples — even though the priest-direct path enforces exactly this rule and a TEMPLE_NOT_VERIFIED message already exists in five languages, emitted by nothing.
- admin-reassign — Fails closed, so nothing is corrupted and no authorization is bypassed, but the API lies. PATCH /bookings/:id accepts priestId in its schema, documents it in a comment, and has a dedicated admin-only 403 branch for it — then never forwards it to the service, returning 200 with the OLD priest's name. Admin is designated the T4 escalation owner and has no working reassignment tool anywhere in the product; no client sends the field today, which is the only reason it is not already an incident.
- notifications — The paid flow's confirmation surface is largely dead. The bookingConfirmationEmail template has zero callers; what actually ships is a tax invoice whose PDF carries the INVOICE date, not the puja date, so a paying devotee never receives in writing WHEN their puja happens. The 'refund' notification event is fully wired to a template and push copy but has no call site, leaving a single email as the only refund notice. Both are gated twice — on RESEND_API_KEY and on a NULLABLE User.email — so a phone-OTP devotee gets nothing at all on any channel, and cancellation vs refund use disjoint channels so no devotee reliably learns both. No money is misrouted; the cost is no-shows and chargebacks against refunds already issued.
- scalability — Nothing here is broken at current volume and no money is misrouted. The one real gap is that puja_bookings.priest_id is unindexed while being the sole predicate of the entire pandit portal (six sequential scans per dashboard load, one of them held open inside the acceptOffer transaction) — a one-line @@index fix. The temple_puja_offering_id half of that claim is refuted (its readers always co-filter on the indexed scheduledDate), the escalation cron self-drains, and the dispatch/refund sweeps already have take limits. Residual: three paginationless admin summary queries, one re-executed per role, behind an error-swallowing catch.
