# UX Audit — 2026-05-01

End-to-end UX sweep of `apps/web/app/**` against the live site
`https://darshya.online`.

## Scope

- 140 `page.tsx` files in `apps/web/app/`.
- 137 routes probed with `curl` (root + every static + a few representative
  dynamic IDs/slugs).
- All client interactivity hot-spots grepped: empty `onClick`, dead `href`,
  `Coming soon` placeholders, calls to deleted endpoints, alert-only handlers.
- `Coming soon` strings, `href="#"`, `href=""`, hardcoded mock data, footer
  link list, social icons, FAQ/help cross-links.

| Status | Count | Note |
|---|---|---|
| 200 | 134 | Every static route, plus dynamic routes with valid IDs and the dynamic routes that have fallback data. |

No production page returns a real broken status. Cloudflare Pages is happy
with every shipped route.

## Pages with console errors

Build was not re-run for this audit (60-min budget). However, no calls to
deleted API endpoints were found via grep:

- No occurrences of `/api/v1/store/orders/<id>` mock pattern in `apps/web/app/**`.
- No occurrences of `/api/v1/wellness/sessions` legacy paths.
- No `console.error` outside of the two known `try/catch` logs in
  `dashboard/page.tsx` and `profile/page.tsx`, which only fire on real
  network failure (graceful, expected).

## Fixes committed inline

1. `fix(help): point Help Center article links at /support/faq instead of href="#"`

   `apps/web/app/help/page.tsx:182` previously rendered `<a href="#">` for
   every article in every category card — the page jumps to top with no
   action taken. Re-routed to `/support/faq?q=<article>` so users land on the
   real FAQ page. Query string is harmless; FAQ page accepts arbitrary URL.

2. `fix(support): point Popular Articles cards at /support/faq instead of href="#"`

   `apps/web/app/support/page.tsx:130` had the same dead link on every
   featured article card. Same fix.

## Top 10 highest-impact deferred fixes (effort/impact ranked)

1. **Real WhatsApp/phone number for support** — Two CTAs on `/help` and the
   bookings detail page route to `+91 8000000000`. Anyone who clicks either
   gets a non-existent number. Effort: 2 lines once owner provides the real
   number. Impact: high (lost support contact).

2. **Real social URLs in footer** — `apps/web/app/layout.tsx` footer renders
   Facebook/Twitter/Instagram/YouTube icons all pointing at `#`. Visible on
   every single page. Effort: trivial. Impact: medium (looks unfinished).

3. **`/pujas` list builds slugs from name** — `apps/web/app/pujas/page.tsx:536`
   constructs `/pujas/${puja.name.toLowerCase().replace(/\s+/g, '-')}` from
   hardcoded mock data. Today the destination route has a generic fallback so
   pages never 404, but every link lands on the same fallback content
   regardless of which card was clicked. Effort: replace mock array with
   `await fetch('/api/v1/pujas')` server-side and use real `slug`. Impact:
   medium (looks like one puja).

4. **`/help` article anchors only fuzzy-match FAQ** — Patched today to
   `/support/faq?q=<title>`, but the FAQ page does not read the `q` URL
   parameter into its search box. Drops users on a clean FAQ. Effort: ~10
   lines in `support/faq/page.tsx` to read `useSearchParams()` and seed the
   search input. Impact: medium.

5. **Status page** — Public-facing "All systems operational" claim on
   `/support` links to `#`. Either link to a real status (Cloudflare/Render
   status pages aggregated) or remove the "Status page →" anchor. Effort:
   small. Impact: low/medium (trust).

6. **Profile avatar upload** — `apps/web/app/profile/page.tsx:262,272`
   advertises "Upload avatar (coming soon)". No backend wiring. Either ship
   the R2 upload (we have the bucket) or hide the affordance. Effort: medium
   (R2 presigned URL + Prisma column). Impact: low.

7. **Priest video upload UI** — `apps/web/app/priest/bookings/[id]/page.tsx:381`
   shows "Or drag and drop video file here (coming soon)" — but video proof
   is *mandatory* per business rule 1 in CLAUDE.md. The actual upload form
   is presumably above this string; verify and remove the misleading
   placeholder. Effort: low. Impact: medium.

8. **Priest in-app messaging** — Same file, line 473: "In-app messaging with
   devotees coming soon." `/messages` route exists at app-shell level. Wire
   the priest booking detail's messaging box to it or remove the affordance.
   Effort: medium. Impact: low.

9. **Direct temple booking opt-out copy** — `apps/web/app/temples/[slug]/page.tsx:48,345,917`
   renders "Direct bookings coming soon for this temple" / "Rich detail for
   this temple is coming soon" / "Full details for this temple coming soon"
   as fallbacks when the API returns sparse data. Confusing because temples
   list is fully populated and bookings *do* work via `/pujas/[slug]/book?temple=<slug>`.
   Effort: medium copy edit. Impact: medium (kills purchase intent on
   long-tail temples).

10. **Pricing "Premium features coming soon"** — `apps/web/app/pricing/page.tsx:192`.
    Fine for pre-launch but should be removed once paid tiers go live.
    Effort: trivial. Impact: low.

## Process notes

- All probes ran from the audit machine against `darshya.online` with
  `curl --max-time 8`, sequentially through a bash for-loop. No CDN-cached
  errors observed; every 200 was an actual rendered page.
- No `pnpm build` was run because the budget was 60 minutes and the audit
  found zero stale-endpoint calls in the source. If a build is desired the
  one-liner is `pnpm --filter @poojly/web build` from repo root.
- API and Prisma were intentionally untouched per scope.
